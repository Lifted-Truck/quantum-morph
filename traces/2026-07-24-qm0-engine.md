# qm0-engine — Q-002: the QM-0 reference engine, tests, and pinned goldens

- **Queue item:** ROADMAP Q-002 (blocked → done). Unblocked by the human's P0
  ratification of `project.manifest.json` this session.
- **Why:** QM-0 is normative and complete, so the engine is a transcription
  problem, not a design problem. Built it as five small pure modules
  (`rng`, `weights`, `noise`, `select`, `warp`) so each spec section has one
  obvious home and a future reader can find §5.1's coupling mask by grepping
  for it.
- **Evidence consulted:** `docs/specs/QM-0-core-engine-spec.md` read in full
  (§2 geometry, §3 selection + §3.3 tie-breaking, §4 modes + §4.1 warp, §5.1
  coupling mask, §7 reshuffle, §8.2 store-don't-reconstruct, §10 acceptance
  tests); `docs/specs/QM-1-m4l-device-spec.md:212` for the js/v8 host question;
  LIBRARY L0001 (do not port the prototype's blend) applied — §5.1 is
  implemented as a mask, and `tests/selection.test.mjs` includes the
  coupling-invariance test that a blend fails.
- **Alternatives rejected:**
  - *Math.random / unseeded draws* — excluded by QM-0 §1; Mulberry32 chosen for
    a single-uint32 state that serializes exactly (see `engine/rng.mjs`).
  - *Storing (seed, epoch) and regenerating the table* — explicitly rejected by
    QM-0 §8.2; the table is authoritative and the rng state travels with it so
    reshuffle histories replay.
  - *Throwing on a discrete+GRADUAL slot inside `selectAssignment`* — rejected:
    §4 says reject at config time, and the selection path runs per field move.
    Split into `validateSlots()` instead.
  - *`>=` in the argmax loop* — rejected explicitly in a comment; §3.3 requires
    lowest-k tie-breaking and `>=` makes the winner iteration-order dependent.
- **Verify:** `fast` exit 0 after the approved `./verify` fix; 41 tests pass.
  Recorded git hash in `.harness/last-verify.json` was `cec1dd0` (the commit
  carrying this trace is its successor).
- **Open questions:**
  1. **Max `v8` is unverified.** The engine uses no Node-only APIs and is pure
     ES modules, but "runs under Max's v8" is an *entailment from the code*,
     not a *verified* fact — there is no Max runtime in an agent session. This
     is the one Q-002 acceptance criterion not fully met; recorded in ROADMAP
     rather than claimed. It also commits the device to `v8` over the legacy
     `js` object, which cannot load ES modules.
  2. The 3-corner triangle is an engine convention (QM-0 §2 does not fix one) —
     ROADMAP Q-002 open question 1.
  3. Goldens encode present behaviour by construction; their value is future
     drift detection. The non-circular evidence is the property tests (census
     vs. analytic bilinear weights, exact tie-breaking, exact salience
     monotonicity), which would fail on a wrong law regardless of goldens.
  4. **A test was wrong, not the engine.** QM-0 §10.4 as literally written
     ("every position not exactly on a boundary") failed at (0.5,0.5) and at
     every x=0.5 / y=0.5 sample point, where the top weights tie and noise
     alone decides. The engine is correct there; the test now skips ties with
     a floor on how many positions must remain, plus a companion test pinning
     the boundary behaviour so a future "fix" cannot make boundaries snap.
